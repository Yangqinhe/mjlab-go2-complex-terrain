# Go2 复杂地形 GPU 并行强化学习项目方案设计

## 1. 设计依据与目标

本方案依据同目录《文件格式.md》及新增的混合地形、可变楼梯高度和域随机化目录要求，重新约定文件管理、模块职责与代码风格。当前阶段交付方案，不代表以下目录和训练功能已经实现。

项目使用 mjlab / MuJoCo Warp 构建 Go2 复杂地形并行环境，强化学习算法沿用已有自写 PPO。正式任务要求每个环境的同一张场景地图同时包含平地、上楼梯、下楼梯、碎石等区域，机器人能够在一个回合内连续穿越不同区域；不能仅将不同环境分别分配为一种地形来代替此要求。楼梯高度由配置范围与难度决定，不使用全训练固定的台阶高度。

先用平地验证控制与算法，再在相同任务框架内启用混合地形和课程。训练默认无窗口，训练后加载 checkpoint 回放并导出视频，供实验分析和 PPT 展示。独立预留域随机化目录，首阶段关闭，后期逐项启用。

最终交付包括可独立运行的项目代码、运行说明、实验记录、最终 `.pt` 权重及对应评估结果，并新建 GitHub 仓库存放代码和最终模型。

已有 RTX 3070 上 2046 个 Go1 平地环境及双机器人步进验证，只作为 GPU 后端可用性参考；不作为 Go2 复杂地形、完整 PPO 训练或收敛结果。首版不引入多机器人协作任务。

### 2.1 模块边界

| 目录 | 负责内容 | 约束 |
|---|---|---|
| `env/` | 场景、控制、观测、奖励、终止、reset | 不执行 PPO 更新，不管理训练目录 |
| `terrains/` | 地形参数、组合地图、几何生成、区域元数据、地形课程 | 不实现 PPO 或传感器噪声，不复制进 `env/` |
| `domain_randomization/` | 后期动力学、传感器、动作随机化与扰动 | 首期默认关闭，不负责混合地图生成 |
| `rl/` | actor、critic、采样数据、GAE、PPO loss 和更新 | 不读取机器人 XML，不创建地形或渲染器 |
| `scripts/` | 命令行、组装环境和 PPO、训练/评估/录像流程 | 不复制奖励公式或网络实现 |
| `models/` | Go2 模型和模型素材 | 不存训练 checkpoint；checkpoint 放 `outputs/` |
| `outputs/` | 每次运行的配置、权重、指标、评估、视频 | 不作为 Python 模块导入，不存源代码副本 |
| `docs/` | 方案、接口、实验分析和交付说明 | 不重复维护会与实际配置冲突的默认参数表 |

业务依赖方向保持简单：`scripts` 使用 `env` 和 `rl`，`env` 读取 `models` 并组装 `terrains`；后期仅在启用时调用 `domain_randomization`。`terrains` 与 `domain_randomization` 不导入项目环境实现或 PPO；通过明确参数和 mjlab 接口工作，不相互依赖。`env` 与 `rl` 通过张量接口交互，不相互导入实现。

只有在职责独立或已有重复代码时才拆文件。不为一两个函数新增管理器、工厂、基类或通用工具框架。mjlab 自带的管理器按其接口使用，不再包一层同名抽象。

### 2.2 路径和资产管理

- 项目内部路径基于文件位置或已明确的项目根目录解析，统一使用 `pathlib.Path`。
- 代码中不写 `/home/user/...` 等个人绝对路径，不依赖运行时恰好处于某个工作目录。
- 模型首次从现有 Go2 项目迁入后，由本项目独立维护；不运行时导入兄弟目录，也不链接外部模型路径。
- 模型来源和修改写入 `models/unitree_go2/SOURCE.md`，保留原始许可证；地形由 `terrains/` 生成，不写入 Go2 本体 XML，不保留第二份 `env/terrain.py`。
- 旧项目作为迁移来源保留，不直接覆盖。新项目中只保留实际使用的版本，不增加 `new`、`final2`、`backup` 等代码副本。

## 3. 同一环境内的混合地形设计

### 3.1 地图组成与 mjlab 的接入方式

首版使用清晰的连续路线，便于速度跟踪、完成率统计和录像。每条路线最少包含：

```text
起点平地 → 上楼梯 → 顶部平台 → 下楼梯 → 过渡平地 → 碎石区域 → 终点平地
```

各区域共享同一世界坐标系、接触模型和机器人状态。区域边界不能依靠传送机器人来跨越，切换地形时不中断回合。路线宽度、区域长度、安全边缘与起终点位置由配置确定；后期可以增加坡地，但不影响首版文件边界。

mjlab 内置地形生成器按子地形生成地块，再拼接为地图；课程模式按地形类型分列、难度分行。直接把 `flat/stairs/rough` 放进 `sub_terrains` 不能保证每个分配地块内部包含整条混合路线。[mjlab 地形文档](https://mujocolab.github.io/mjlab/v1.6.0/source/terrain.html)

因此，本项目在 `terrains/mixed_terrain.py` 定义一个组合子地形：在同一地块内调用平地、上下楼梯和碎石生成函数，最终作为一个 `mixed_course` 类型交给 mjlab。保留 mjlab 的地块生成、模型编译和难度分配流程，不另写仿真器或通用场景框架。具体子地形配置类和调用签名以已安装 1.6.0 的接口为准，实现时先核对再做最小适配。

`num_envs` 是独立物理世界的数量；地形地图可以在模型层共享，各世界拥有独立机器人状态，并使用分配的路线起点。2046 个环境不要求生成 2046 份独立网格或模型。每个被分配的混合路线都包含全部必需地形；多个环境可以复用同一路线，随后再扩展路线变体。

### 3.2 几何与区域信息

| 地形 | 首版实现 | 主要参数 |
|---|---|---|
| 平地与平台 | 静态平面或长方体 | 长、宽、高程、起点和安全距离 |
| 上楼梯 | 静态长方体台阶 | 台阶数、单级高度序列、踏面深度、宽度 |
| 下楼梯 | 静态长方体台阶 | 对应下降高度序列、落地点高程 |
| 碎石 | 固定不规则块体/障碍，首版优先少量简单碰撞体 | 高度范围、尺寸、密度、间距和布局 seed |

碎石首版表示静态不平整地面，不代表可滚动的真实散落石块。可移动碎石会增加刚体、接触和状态管理成本，作为后期单独扩展。楼梯优先使用有明确竖直立面的几何体，不用平滑噪声高度场代替实际台阶。

每块路线记录 `layout_id`、`terrain_seed`、难度、各区域边界与高度参数、起点和目标点。这些数据供 reset、区域进度统计、评估和视频说明使用，通过普通配置/字典传递，不引入大型地图管理类。

拼接时检查平地与首级台阶、顶部平台、末级台阶与碎石过渡处的高程连续性，避免无意形成裂缝、悬空或隐藏障碍。碎石布局保留可通行间隙，不把初始脚落点放在障碍边缘。

### 3.3 楼梯高度不固定

把“楼梯高度”明确为单级台阶的竖直高度，累计爬升为单级高度之和。所有高度以米保存，文档可换算为厘米。

首版采用“每段楼梯内部等高，不同路线/难度使用不同高度”：

```text
h(d) = h_min + d * (h_max - h_min),  d ∈ [0, 1]
总爬升 H = 台阶数 × h(d)
```

初始候选范围为 0.02～0.12 m（2～12 cm），仅作为待验证的配置起点，不代表 Go2 已能通过。平地阶段单独关闭楼梯起伏；升阶范围和最终上限根据训练表现调整。踏面深度、台阶数和平台宽度同时进入配置，不只改变高度而忽略整条路线长度与总爬升。

高度变化体现在预生成的不同难度路线、不同布局变体及训练课程中；reset 可切换已有路线或难度，不在机器人落脚时改变地面高度。

后期可选“同一段内非等高”，默认关闭：每级高度 `h_i` 在基础高度周围采样，并限于配置范围；累计高程使用 `z_k = z_0 + sum(h_i)`。上下楼梯采用匹配的总高度，首版可镜像上行序列构造下行序列，确保最后回到预期平地高程，不能逐级独立采样后留下意外落差。记录完整高度序列和布局 seed 以便复现。

台阶高度不能通过“机器人质量随机化”等动力学设置代替。`terrains` 的几何变化在首期就启用，与后期域随机化开关独立。

### 3.4 生成时机、reset 与地形课程

1. 启动时：根据地形配置和独立 seed 生成混合路线与难度等级，编译并上传 GPU；保存实际生成参数。
2. 回合中：地形碰撞几何保持固定，机器人按命令连续穿越各区域。
3. 回合结束：只对结束的环境恢复机器人状态，清理动作/相位/历史，并根据课程选择已有路线起点和等级。
4. 确需产生全新几何时：在独立构建阶段重新生成并重建所需仿真资源，不能假设修改共享模型后只影响某一个环境，也不能在每个 reset 重编译整个批量场景。

`terrains/curriculum.py` 根据完成距离、跌倒和分区域表现调整等级。建议顺序为平地控制验证 → 低台阶/稀疏碎石的完整混合路线 → 逐步增加台阶高度和碎石起伏 → 随机起点或反向穿越。训练可从不同区域前的平整位置起步，避免只学会最前段；最终评估必须从完整路线起点连续通过全部区域。

地形 ID、难度级别、区域进度保存在环境侧，不默认加入 actor 观测。机体高度、足端抬升与滑移判定应参考当前位置的实际支撑地形，不能继续使用全场固定 `z=0`。是否给 actor 加地形扫描作为显式任务配置决定；若增加输入，需同步更新维度、网络与 checkpoint 版本，不静默改变原观测。

### 3.5 地形复现与最低验收

每次运行在 `outputs/<run>/terrain_manifest.json` 保存路线顺序、布局 seed、难度、高度序列、几何尺寸、配置/代码版本及可复现所需参数。同一地图复现需要同一生成逻辑及版本，不能只保存一个 seed。

先完成少量有针对性的检查：单环境可观察到所有区域；上下楼梯高度和累计高程正确；reset 起点不穿地；机器人能实际接触各段；不同并行环境没有状态串扰。随后再做 2046 环境的完整 PPO 性能验证。

评估同时统计整条路线通过率、每个区域的到达率/通过率、区域内速度误差和跌倒率，并注明各指标分母；按台阶高度分组报告结果。不能只在起点平地存活就视为复杂地形任务成功。

## 4. 域随机化目录与后期边界

### 4.1 首期保留方式

`domain_randomization/` 独立管理，首期 `enabled=False`。只保留 README 和最小配置，不实现未使用的随机化函数、基类或插件系统。目录树中标注“后期”的 Python 文件在需要时创建，不能把空实现描述为已有能力。

关闭时不随机修改动力学参数、不注入观测噪声、不延迟动作、不施加随机外力。现有环境若自带这些事件，必须显式梳理和关闭，避免配置显示关闭但后端仍在执行。地形采样、速度命令和 reset 随机采样不受此总开关控制，各自记录 seed 和配置。

### 4.2 后期职责与采样时机

| 文件 | 后期功能 | 计划采样时机 |
|---|---|---|
| `dynamics.py` | 质量/惯量、摩擦、电机强度、阻尼 | 初始化或回合 reset，按后端可支持的模型字段实现 |
| `observations.py` | IMU/关节噪声、回合固定偏置 | 偏置在 reset；白噪声在观测更新时 |
| `actions.py` | 动作延迟、执行偏置 | 延迟配置在 reset；动作队列每个控制周期推进 |
| `disturbances.py` | 有限持续时间的外力扰动 | 按配置的仿真时间间隔触发，明确力和作用时长 |

独立模块开关、范围、采样频率和 seed 放 `domain_randomization/config.py`。动力学参数随机化优先使用 mjlab 已有事件及模型字段接口；未确认支持每世界独立变化的参数，不直接修改共享模型假装实现独立随机化。

动作延迟缓冲区和传感器偏置按环境保存，并在该环境 reset 时单独清理。原始仿真状态与带噪 actor 观测分开管理，避免评估指标和奖励被无意污染。每次实验保存启用项及范围，后期逐项对比固定参数基线，再组合启用。

## 5. 参数集中管理

参数按所属模块集中，避免同一参数同时出现在环境、训练脚本和配置文件中。

| 位置 | 参数示例 |
|---|---|
| `env/config.py` | 物理步长、decimation、PD 增益、动作尺度、关节限位、奖励权重；引用地形与域随机化配置 |
| `terrains/config.py` | 混合路线尺寸/顺序、台阶高度范围、碎石布局、地形 seed 和课程范围 |
| `domain_randomization/config.py` | 默认关闭、后期启用项、参数范围、采样时机和独立 seed |
| `rl/config.py` | 网络维度、学习率、gamma、lmbda、epsilon、epochs、batch_size、rollout 长度 |
| 训练入口 | seed、device、num_envs、训练预算、输出目录、resume 路径 |
| 评估/录像入口 | checkpoint、评估指令、地形、回合数、镜头、分辨率、fps |

新建环境模块尽量在 `__init__` 一次传入该模块需要的配置，例如 `Go2Env(config, device)`，不要依赖可变全局配置。配置对象可以用普通字典或简单 dataclass，选择一种即可，不增加配置框架依赖。

已有 PPO 的 `__init__`、变量名和方法接口优先保留：入口从集中配置中读取参数，再映射到现有构造参数；不为统一形式而强制改成新的配置接口。原来写在 PPO 构造函数内部的常调参数，如 `batch_size`，可增加明确的可选构造参数，默认行为保持一致，并记录变更。

配置加载顺序固定为：默认配置 → 本次显式覆盖 → 恢复训练的兼容性检查 → 保存实际生效配置。恢复训练不能静默覆盖观测顺序、动作尺度、网络结构或关节顺序等接口参数。

每次运行保存 JSON 配置快照，记录实际数值；`Path`、设备等转换为字符串。首版不同时维护 JSON、YAML 和多套 Python 配置。设备选择只在入口处理，核心模块接收 `device`，不硬编码显卡编号或 UUID。

## 6. 沿用自写 PPO 的代码管理

### 6.1 来源与修改范围

以已有 `mujoco_project_go2_stairs/rl/algorithms/ppo.py` 和 `ActorCritic.py` 为迁移基线，沿用 `PPO`、`ActorNet`、`CriticNet` 及 Gaussian 动作、clip loss、GAE、KL 早停等实现思想。首次迁入时在 `docs/PPO迁移说明.md` 记录来源路径、版本或文件哈希与修改原因。

不使用 mjlab 默认训练入口替换自写算法，也不因为 mjlab 的依赖中包含其他 RL 库就改用其 PPO。训练入口负责对接 mjlab 环境和已有 PPO。

原 PPO 当前存在单环境 `.item()`、NumPy 缓存和 CPU 动作输出；这些位置必须为并行 GPU 采样做必要修改，不能只设置 `num_envs`。优先局部替换，保留 buffer 字段名和调用流程。确需增加批量接口时明确说明输入输出，保留可行的单环境调用兼容性，不使用隐式猜测 shape 的复杂分支。

### 6.2 数据约定与必须写清楚的注释

记 `T` 为采样长度、`N` 为环境数、`O` 为观测维度、`A` 为动作维度：

| 数据 | 约定形状 |
|---|---|
| 当前观测与动作 | `[N, O]`、`[N, A]` |
| states、actions | `[T, N, O]`、`[T, N, A]` |
| rewards、values、next_values、log_probs、dones、terminated | `[T, N]` |
| PPO mini-batch | GAE 完成后将前两维展开为 `T * N` |

这些是新项目的批量接口目标；观测维度及顺序以正式环境说明为准，不把原有 58 维或 Go1 的输入直接视为兼容。

- GAE 沿时间维反向递推，各环境独立计算，不能先展开时间与环境维。
- 终止标志 `dones` 用于切断 GAE；`terminated` 用于控制 bootstrap。超时必须使用 reset 前的最终观测计算 next value，不能使用自动 reset 后的观测。
- rollout 内保存采样时的 old policy 信息，PPO 更新时保持固定。
- 保留原始 Gaussian 样本用于 log probability；环境内限幅后的执行动作不能替代该样本。若将来改变为 tanh-squashed distribution，需作为独立算法变更处理。
- 动作进入关节目标和 PD 的映射只在环境维护一份。观测缩放由选定模块统一负责，训练、回放和导出不得重复缩放。
- 热路径保留 GPU 张量，不逐环境 `.cpu().numpy()` 或 `.item()`；日志按更新周期汇总后转换。

以上位置必须添加解释原因的注释。对关键算法做针对性的数值核对；不建立与当前任务无关的大量鲁棒性测试。

## 7. outputs 与 checkpoint 管理

### 7.1 一次训练一个目录

采用本地时间（Asia/Hong_Kong）加任务名和 seed 命名，例如：

```text
outputs/20261031_153000_go2_stairs_seed42/
├── config.json                    # 实际生效的训练与环境配置
├── metadata.json                  # 版本、GPU、代码版本、来源 checkpoint
├── terrain_manifest.json          # 混合路线、台阶高度、布局和难度
├── randomization.json             # 当前关闭状态；后期启用项与范围
├── train.log                      # 训练过程日志
├── metrics.csv                    # 更新次数、总步数、loss、KL、奖励分项
├── checkpoints/
│   ├── latest.pt                  # 最近的可续训 checkpoint
│   ├── best.pt                    # 根据固定评估规则选出的 checkpoint
│   └── final.pt                   # 本次预算结束时的 checkpoint
├── evaluations/
│   └── eval_000100.json            # 对应 checkpoint 的定量评估
└── videos/
    ├── final_stairs_side.mp4
    └── final_stairs_side.json      # 视频来源、指令、seed、镜头和 fps
```

目录冲突时增加序号，不覆盖已有运行。续训默认创建新目录，在 `metadata.json` 中记录父运行及加载权重；同一运行目录内允许更新 `latest.pt`、`best.pt`。评估和视频文件按评估编号或场景命名，不静默覆盖已有结果。

`best.pt` 的选择标准要记录在配置中，例如固定评估集的通过率及速度误差。没有评估结果时不自动把最后一个 checkpoint 称为 best。`final.pt` 表示训练结束状态，不表示已达到性能目标。

### 7.2 checkpoint 内容

保留已有 actor、critic、优化器和统计字段命名，按需要增加 `format_version`、更新次数、总环境步数、配置与观测/动作定义。字段变化需要版本说明和显式兼容检查，不静默部分加载后继续训练。

支持恢复模型、优化器和随机状态；若未保存完整仿真状态，则恢复后开启新回合，并在文档说明它不是逐步完全一致的断点复现。PPT 使用的模型必须能追溯到对应运行目录、评估数据与代码版本。

## 8. 无窗口训练与 PPT 视频

训练入口默认不创建交互窗口、不启动 viewer，也不逐步录像。若将来使用视觉观测，必要的离屏传感器渲染与可视化窗口分开配置。

训练完成后，`record_video.py` 加载指定 checkpoint 和配置，以确定性动作回放，用离屏渲染保存 MP4。复用训练环境的动作映射、观测顺序、归一化和 PD 参数，只覆盖评估所需的环境数、指令、地形和镜头。

录像首版建议使用 1 个环境、1280×720、30 fps。仿真推进时间与输出帧率对应，不能把每个物理子步都直接当成一帧造成播放速度错误。先保存一段完整混合路线录像，长度以完整穿越所需时间为准，包含平地、上楼梯、下楼梯和碎石；再导出 10～20 秒重点片段用于 PPT。录像标注台阶高度和难度，固定镜头全景与机器人跟随镜头可分开导出。

视频及旁边的 JSON 记录：模型路径或哈希、运行目录、任务、seed、速度指令、地形参数、仿真时长、fps 和回放结果。评估指标另存 JSON，PPT 中不把经过挑选的视频片段当成整体通过率证据。后处理录像是策略重新运行，不等同于训练时某个回合的原始录像。

### 8.1 计划入口

以下是后续实现的命令约定，目前不是已可执行的功能：

```bash
python -m scripts.train_go2_ppo --num-envs 2046 --seed 42
python -m scripts.play --checkpoint outputs/<run>/checkpoints/final.pt
python -m scripts.evaluate --checkpoint outputs/<run>/checkpoints/final.pt
python -m scripts.record_video --checkpoint outputs/<run>/checkpoints/final.pt
```

入口参数保持少量且含义明确。启动脚本只解析参数、建立对象和调用流程；不在脚本之间互相复制训练或推理代码。

## 9. 代码风格约定

### 9.1 可读性优先

- Python 使用 4 个空格缩进，一行完成一条清晰语句，避免分号串联和过长表达式。
- 新函数与变量使用 `snake_case`，类使用 `PascalCase`，常量使用 `UPPER_SNAKE_CASE`。已有 `ActorCritic.py`、`lmbda`、`epsilon` 等名称不为风格统一而随意更改。
- 用 `obs`、`action`、`reward`、`terminated`、`truncated` 等明确名称；必要的 `T`、`N` 维度符号在使用处解释。
- 普通函数优先；需要持有环境、网络或优化器状态时使用类。避免无必要的装饰器、继承层次、工厂和设计模式。
- 网络推理使用 `torch.no_grad()` 或 `torch.inference_mode()` 等有明确用途的机制，不自建装饰器体系。
- 不把复杂逻辑压成一行。关键中间量保留名称，方便核对公式、张量维度和控制行为。
- 只在必要边界检查 shape、配置和 checkpoint 兼容性；不在每个物理子步重复执行大量检查或 GPU 同步。
- 错误保留明确异常，不用宽泛 `except Exception` 吞掉训练错误或自动换用 CPU 继续运行。

### 9.2 模块化与最小修改

修改前先找已有实现和调用方，只改完成目标所需的文件与逻辑。保留原接口、变量名、网络结构和数据字段；若算法或 GPU 批量化确需修改，先写清影响，再同步调整必要调用方。

奖励函数只计算分项，权重在环境配置中维护；观测构建只负责顺序和计算，不额外修改命令或推进仿真。文件输出集中在入口流程，不在 PPO loss 或 reward 内写文件。

不为了简单配置新增第三方依赖。优先使用标准库、现有 PyTorch、NumPy、MuJoCo 和 mjlab 能力。确需补充录像编码等依赖时，说明用途并记录到依赖文件，不只在个人环境里临时安装。

### 9.3 文件说明和注释

每个 Python 文件开头写模块 docstring，说明主要职责；重要函数再说明输入输出、坐标系、单位或关键 shape。注释优先使用清楚的中文，标识符沿用现有英文命名。

```python
"""实现 GPU 批量 PPO 更新；GAE 沿时间维递推，各环境独立截断。"""

# 时间截断需要保留最终观测的价值，不能使用自动 reset 后的新回合观测。
next_values = critic(final_obs)
```

上述代码仅示意注释方式，实际实现需要区分普通步、终止步和超时步。不能把条件处理省略后直接用于所有 transition。

必须解释的关键位置包括：四元数顺序、世界系/机体系转换、关节顺序、动作限幅与 log probability、PD decimation、超时 bootstrap、批量 GAE、接触与滑移奖励、录像时间采样。

避免逐行重复语句含义的注释，也不把未验证结果写成已经达到的效果。

## 12. 实施顺序与验收边界

1. 建立上述最小目录，迁入 Go2 模型和自写 PPO，记录来源与依赖版本；保留旧项目原文件。
2. 完成 Go2 单环境站立、观测/关节顺序和 PD 验证，再适配批量环境及 PPO 数据维度。
3. 做必要的 GAE/截断核对和短程训练，检查 loss、KL、奖励分项及 checkpoint 加载。
4. 在 `terrains/` 实现完整混合路线，先核对拼接高程、不同台阶高度、区域元数据和 reset，再启用地形课程；每个正式任务环境都保留全部必需地形。
5. 对无窗口 Go2 混合地形环境逐步增加并行数量，再实测 2046 环境的完整采样与 PPO 更新；分别记录初始化、采样、更新耗时、显存和接触容量告警，不照搬 Go1 平地基准。
6. 对不同台阶高度和各区域做独立评估，记录整条路线通过率，完成完整录像与 PPT 片段。
7. 首期保持域随机化关闭并保存基线；后期在独立目录中逐项实现和对比，不把首期未完成项作为训练前置条件。
8. 选定最终模型，完成独立加载、定量评估和 PPT 视频，更新 README 和 CHANGELOG 后上传 GitHub。

验收以模块职责清楚、参数可追溯、PPO 算法准确、训练/回放一致、结果可复现为主。保留能发现关键错误的少量验证，不为低影响改动扩展测试框架，也不进行与目标无关的重构。
